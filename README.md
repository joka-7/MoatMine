# MoatMine

*Dig for companies that can't be knocked down.*

Risk-aware investing app: every stock gets a graded safety score, every buy is checked against the user's own risk rules, and the portfolio is stress-tested against past crises. One UI for **web (GitHub Pages)** and **desktop (Tauri)**, backed by one **FastAPI service on Render**.

## Features

| Area | What you get |
|---|---|
| **Safety score** | 0–100 final score and A–F grades by area (financial health, quality & earnings, price risk, crisis resilience, size, valuation, **moat**: return on capital, margin stability and steady growth over up to 10 years), red flags, a rule-based summary and an AI analyzer that explains the grades against the user's rules |
| **Risk profile** | 5-question questionnaire → conservative / moderate / balanced / growth, with editable rules: max position %, max sector %, minimum safety score, max volatility, portfolio loss limit, minimum company size, penny stocks, cooling-off hours, paper mode |
| **Safety check & buy plans** | Every buy is checked against the rules: pass, warn (needs a written reason + cooling-off wait) or block. The reason is saved to the stock's journal. Paper accounts enforce blocks and buy at the live price, paid from their cash; removing a paper position sells it at the live price. An account can't switch between real and paper. Real accounts warn. Position size counts a buy as paid from cash first |
| **Portfolio risk** | Volatility, beta, 1-month value-at-risk, worst fall, concentration, sectors vs limit, correlation heatmap, rule breaches (also raised as alerts by the worker, together with a fall from the 1-year high past the loss limit) |
| **Stress tests** | Today's holdings replayed through the dot-com crash, 2008, 2011, Q4 2018, COVID and 2022, plus 10/20/35% market falls, against the user's loss limit |
| Accounts & portfolio | Accounts with cash, holdings, live P/L, weights, day change, allocation donut, value-over-time chart |
| **Real vs paper** | Paper (practice) accounts are a separate book. Real-money totals, risk, stress tests, alerts and position-size checks never include paper money. The dashboard, Portfolio and Risk pages have a Real money / Paper toggle, and the agent's portfolio tools take `mode: real \| paper` |
| Watchlist | Symbols with notes and price alerts (above / below) |
| Stock page | Candles or line chart, 1D–5Y ranges, SMA20/50 and volume overlays, zoom in/out/fit plus wheel and drag |
| Ratios | Valuation, profitability and health ratios from the provider; return, volatility, max drawdown, Sharpe, Sortino, RSI and SMA computed from candles, with a selectable lookback |
| Company info | Description, sector, industry, employees, CEO, IPO, website, market cap |
| Earnings & dividends | EPS actual vs estimate with surprise %, dividend history chart, stock splits |
| Analysts | Recommendation trend (strong buy … strong sell) and consensus price target vs current price |
| **Value estimator** | Eight fair-value models side by side: 2-stage DCF, Graham number, Graham formula, Peter Lynch, dividend discount, earnings power value, P/E multiple and EV/EBITDA multiple. Summary shows the median fair value, low–high range, a margin-of-safety "buy below" price and a verdict. Every assumption is editable (discount rate, growth, terminal growth, years, MOS, bond yield, fair multiples). |
| Valuation indicators | PEG, earnings yield, FCF yield, P/FCF, P/B, dividend yield, payout ratio, EV/EBITDA, net debt/EBITDA |
| Bad times | How the stock did in the dot-com crash, 2008, 2011, Q4 2018, COVID and 2022 vs SPY (or any benchmark): fall, time to recover, downside capture, and its own worst drawdowns |
| Quality scores | Piotroski F-score with all 9 checks, and Altman Z-score with its zone |
| News | Per-stock news by date window, an AI digest with sentiment (fast model, cached 1h), and a dashboard feed across holdings and watchlist |
| My info | Your own notes, thesis, news and links per stock |
| **PAPI / MAMI targets** | **P**rofit %, **A**mount (value), **P**eriod (days held), **I**ntent (category plus risk as annualised volatility %). Each has a target and **MA**x/**MI**n bounds. Scope is one symbol or the whole portfolio. Shown as live range bars. |
| Alerts | Worker evaluates targets and watch prices and writes de-duplicated alerts (bell menu) |
| AI agent | Tool-using chat through **[ModelDispatcher](https://github.com/joka-7/ModelDispatcher)**, bound to the user's risk profile. Read tools: `get_portfolio`, `get_quote`, `get_ratios`, `get_news`, `get_company`, `get_earnings`, `get_analysts`, `get_dividends`, `get_valuation`, `get_bad_times`, `get_risk_profile`, `get_safety_score`, `safety_check`, `get_portfolio_risk`, `get_stress_test`, `get_news_feed`, `get_targets_status`, `get_watchlist`, `get_notes`. Write tools (`add_to_watchlist`, `save_note`) act only on a symbol the user named in their own message |
| AI settings | ModelDispatcher's shared `<ModelPicker>`: providers in fallback order, a model each, pooled keys (encrypted server-side), a favorite free AI app (`<AskExternallyButton>` / `<PasteExternalReply>` in chat), plus an **external agent** at any OpenAI-compatible base URL |
| MCP | `/mcp/` exposes the read tools to Claude Desktop, Claude Code or any MCP client, using per-user revocable tokens. The write tools aren't served |

### AI via ModelDispatcher (`backend/app/ai/dispatcher.py`)

All AI calls (chat, news digest, safety analyzer) go through `model-dispatcher` (PyPI) and the web
uses `modeldispatcher-react-ui` / `modeldispatcher-browser-agent` (npm), both 0.6.7.

- Per request the backend builds a provider registry from the user's AI settings plus any vendor the
  server has a key for (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`).
- `auto`: ModelDispatcher triages the question and routes cheapest-capable first, falling back across
  vendors and across a user's pooled keys. A vendor id pins that vendor; `external` uses the user's agent.
- The user's own key always wins over the server key for the same vendor.
- Per-user quotas (`AI_REQUESTS_PER_MIN`, `AI_TOKENS_PER_MIN`, `AI_TOKENS_PER_DAY`); when the shared
  key runs out the API returns ModelDispatcher's handoff and the chat links to AI settings.

The agent has no tool that places trades.

## Install

- **Web app:** `https://<owner>.github.io/<repo>/` once GitHub Pages is set up (see Deploy).
- **Desktop Chrome or Edge, Android Chrome:** open the web app → browser menu → *Install app*. It opens in its own window and on the home screen (`web/src/app/manifest.ts`).
- **iPhone:** open the web app in Safari → Share → *Add to Home Screen*.
- **Desktop app:** download the installer for Windows (`.msi` / `.exe`), macOS (`.dmg`) or Linux (`.AppImage` / `.deb`) from the latest GitHub release. The builds are not code-signed, so Windows SmartScreen and macOS Gatekeeper warn on first launch (macOS: right-click the app → *Open*).
- **Android app:** download `MoatMine_<version>_android.apk` from the latest release and open it; allow installing from your browser when asked. Install new versions over the old one.

## Getting started

Prerequisites:
- Python 3.12+ (Render and CI run 3.12) for `backend/`
- Node.js 22 (what CI uses) for `web/` and `desktop/`
- Rust and the [Tauri system dependencies](https://tauri.app/start/prerequisites/), only for `desktop/`
- No API keys: with none set the API serves labelled sample prices. `FERNET_KEY` is only needed
  to save AI keys; the command that generates one is in `backend/.env.example`.

```bash
git clone --recurse-submodules <repo-url>   # .ai is the ogen-ai submodule
python .ai/bin/ai-sync                      # only after editing ai-config.toml / ai-config.local.md
```

Contributing (commit style, what to regenerate when, the checks to run): [`CONTRIBUTING.md`](CONTRIBUTING.md).

### Run locally

```bash
# API
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env    # set FERNET_KEY (command is in the file); add an AI key to try the agent
alembic upgrade head    # create/upgrade the schema
python -m app.seed      # demo data for user "dev"
uvicorn app.main:app --reload
pytest                  # tests
ruff check . && mypy    # lint + strict type check (config in pyproject.toml)
python -m app.openapi_spec ../web/openapi.json   # after changing a response model; then `npm run gen:api` in web/

# Web
cd web
cp .env.example .env.local
npm install && npm run dev        # http://localhost:3000
npm run lint                      # ESLint (config in eslint.config.mjs)
npm test                          # vitest unit tests (src/**/*.test.ts[x])

# Desktop (needs Rust + Tauri system deps: https://tauri.app/start/prerequisites/)
cd desktop
npm install
npm run dev     # opens a native window on top of the Next dev server
npm run build   # static-exports web/ and bundles installers (.msi/.dmg/.deb/.AppImage)
```

**CI** (`.github/workflows/ci.yml`) runs on every push to `main` and every PR, in four parallel jobs:
- backend: `ruff`, `mypy --strict` and `pytest` on Python 3.12, and a check that `web/openapi.json` matches the routes
- web: `tsc`, `npm run lint` (ESLint: Next.js rules plus typescript-eslint strict), a check that the generated API types are current, `npm test` (vitest), `npm run build` and `npm run build:desktop`
- desktop: `cargo check` for the Tauri shell
- docs: the generated repo maps in `README.md` and `docs/STRUCTURE.md` match the tree

It checks out the `.ai` submodule. If that repo isn't readable with the default token, add a `SUBMODULE_TOKEN` secret.

The app runs with **no API keys**: `MARKET_PROVIDER=mock` serves deterministic sample prices, and the UI labels them as sample data.

## Deploy

**Clerk first.** Create a Clerk application. You need three values from it: the publishable key, the JWKS URL (`https://<frontend-api>/.well-known/jwks.json`) and the issuer (`https://<frontend-api>`). The API refuses to start with `AUTH_MODE=dev` on Postgres, and with `AUTH_MODE=clerk` if either Clerk value is missing.

**Render.** New → Blueprint → this repo. Then fill in the prompted secrets:
- `FINNHUB_API_KEY`. The blueprint sets `MARKET_PROVIDER=finnhub`, but without this key the API serves the labelled sample data. Before you rely on it:
  - Finnhub's free plan is for personal use. Check the terms before showing its data to other users.
  - Free Finnhub gives quotes, news, ratios, earnings, recommendations and splits.
  - `/stock/candle` may need a paid plan. Until then, charts fall back to sample data. Every result built on those bars (safety score, portfolio risk, stress tests, bad-times history, holdings value chart, price ratios) is labelled `mock-fallback`, and target alerts treat the volatility as unknown instead of using sample prices.
- `FMP_API_KEY` (optional). Company descriptions, statements (Piotroski, Altman), price targets and dividend history need it or a paid Finnhub plan; without them those sections say so instead of breaking. The FMP mapping follows FMP's documented `/stable` fields but hasn't been run against a live key yet.
- `FERNET_KEY`
- `CLERK_JWKS_URL` and `CLERK_ISSUER` (the blueprint sets `AUTH_MODE=clerk`)
- `CLERK_AUTHORIZED_PARTIES` = your web app's origin (`https://<owner>.github.io` on GitHub Pages) plus `tauri://localhost,http://tauri.localhost`, so sessions minted for another site on the same Clerk instance are refused
- AI keys (optional)
- `CORS_ORIGINS` = the same web origin plus `tauri://localhost,http://tauri.localhost`

**Web (GitHub Pages).** Render runs the API, the worker and the database; the web UI is only static files, so GitHub Pages can serve it. `.github/workflows/pages.yml` builds the static export and publishes it at `https://<owner>.github.io/<repo>/` on every push to `main` that touches `web/`. Once:
1. Settings → Pages → Source: **GitHub Actions**.
2. Settings → Secrets and variables → Actions → **Variables**: `API_URL` = `https://<moatmine-api>.onrender.com` and `CLERK_PUBLISHABLE_KEY` = the Clerk publishable key. Neither is secret: both end up in the page anyway. The workflow stops with an error until `API_URL` is set.
3. In Clerk, allow the Pages origin. Check whether your Clerk plan's production instance accepts a `github.io` address or needs a domain you own.

With the key set, the whole app sits behind Clerk's sign-in, and every API call sends the Clerk session token from `getToken()`. Vercel also works (import the repo with root directory `web` and set `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`), but nothing needs it.

**Desktop.** Set `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` before `npm run build` so the installer points at Render and signs in with Clerk. Users can also change the API URL in Settings. The static export swaps `@clerk/nextjs` for `@clerk/react` (see `web/next.config.ts`), because the Next.js provider needs a server.

The desktop CSP in `desktop/src-tauri/tauri.conf.json` allows Clerk development instances (`*.clerk.accounts.dev`). For production you must add these to `script-src` and `connect-src`:
- your production Clerk frontend API domain
- your API domain, if it isn't on `*.onrender.com` (narrow `*.onrender.com` to your API host if users won't point the app elsewhere)

The production `csp` has no `'unsafe-inline'` for scripts: Tauri hashes each inline script of the static export into the policy at build time. `devCsp` (used by `npm run dev`) keeps `'unsafe-inline'` and `http://localhost:8000` for the Next dev server and a local API.

**Releases (desktop and Android).** `.github/workflows/release.yml` publishes release `v<version>`, creating the tag, with the desktop installers and the Android APK (`.github/workflows/android.yml`). The version comes from `desktop/src-tauri/tauri.conf.json`. A push to `main` releases automatically when that version has no tag yet, so a release is: bump the version, add a `CHANGELOG.md` entry, merge. It needs the same `API_URL` and `CLERK_PUBLISHABLE_KEY` repository variables as the Pages build, so the apps point at your API. Android only installs signed APKs and only accepts updates signed with the same key, so create one keystore once and store it as secrets:
```bash
keytool -genkeypair -keystore moatmine.jks -alias moatmine -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 moatmine.jks   # → secret ANDROID_KEYSTORE_B64; the password → secret ANDROID_KEY_PASSWORD
```
Keep `moatmine.jks` and its password safe: losing them means users must uninstall to get the next version. Without the secrets the APK is signed with a throwaway key. Desktop installers need no keys (they are unsigned, as above).

Desktop and Android sign-in have only been built, not exercised against a live Clerk instance; Google's sign-in button is likely to be blocked inside the app windows, as Google blocks embedded webviews. Before shipping desktop builds, check that your Clerk instance accepts the Tauri origins (`tauri://localhost`, `http://tauri.localhost`).

## Before real users

- **Auth.** `AUTH_MODE=dev` trusts the bearer token as the user id. It works only against a local SQLite database: the API refuses to start in dev mode on Postgres. Production runs `AUTH_MODE=clerk` (see Deploy).
- **Schema.** Alembic owns the schema (`backend/migrations/`). Render runs `alembic upgrade head` before each deploy of the API and the worker. After changing `app/models.py`, run `alembic revision --autogenerate -m "..."`, review the file, and commit it with the model change. `tests/test_db.py` fails if the models and migrations drift apart. A database created before migrations is adopted by the baseline revision as-is.
- **Market data.** Check the Finnhub and FMP caveats under Deploy → Render before showing data to other users.
- **Broker sync.** SnapTrade or Plaid Investments can fill the existing `accounts` and `holdings` tables. Today they are entered manually.
- **Chat.** Chat replies are not streamed yet (one response per turn).
